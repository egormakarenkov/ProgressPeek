# Local release preparation and updates

0.4.0-beta is a local unsigned candidate, not a public licensed release. License, publisher contact/repository, compiled public trust key, Authenticode/reputation policy and real clean-PC verification are pending publisher gates. Do not publish until resolved. Already-shipped unconfigured TaskProgress 0.3 cannot learn a publisher; users need a one-time manual ProgressPeek installation. Legacy state is copied non-destructively, and the legacy TaskProgressOverlay mutex is intentionally retained for admission compatibility. Main-task self-reported progress is deferred and requires explicit prompt/tool integration; no exact cost comparison with repeated estimator checks has been established.

For portable/source/installer packaging use package.ps1 with the candidate executable, a new empty destination and optional external official Inno 7 ISCC.exe. ZIP entries are exact allowlists with fixed timestamps; SHA256SUMS.txt covers generated assets. The installer is per user, never launches the app, never kills a process, and leaves local data on uninstall. Close running old/new versions manually before upgrading. Test-Installer.ps1 compiles a unique disposable AppId with shortcuts disabled and never runs the candidate; it cannot certify a clean machine. Test-Distribution.ps1 verifies archive manifests and reproducibility. No publishing or signing secrets are configured in CI.

Identical already verified pending release bytes reuse the same stage after target/helper/payload revalidation. Existing rollback assets remain bounded as .previous and .failed files; unknown staging directories are retained rather than broadly deleted. Repeated different stages can accumulate and require an explicitly scoped manual cleanup. Rollback files are not portable ZIP entries.

This source build deliberately has an empty compiled repository and public key. Updates show **Not configured** and make no update requests. This build cannot learn a publisher identity later from a server or an editable setting. Before the first public release, configure `DistributionConfig.Repository` with the exact GitHub owner/repository and `UpdatePublicKeyXml` with the publisher RSA public key, then build and distribute that configured executable once. Subsequent versions must retain that trust identity. Publisher private keys must remain outside source, source ZIPs, release assets, and user settings. This task creates no production key, repository, or upload.

Use an externally managed RSA XML private key of at least 2048 bits and a newly built executable. Run from Windows PowerShell 5.1 (`powershell.exe`): `prepare-release.ps1 -ExecutablePath <binary> -Repository <owner/repository> -PrivateKeyPath <external-key> -OutputDirectory <new-empty-directory>`. PowerShell 7 is unsupported because release validation uses .NET Framework reflection-only assembly loading. The script validates compiled publisher trust, assembly/file/informational versions, executable bounds, copied bytes, and a local RSA SHA256 verification. It produces exactly `ProgressPeek.exe`, `ProgressPeek.update.json`, and `ProgressPeek.update.sig`. It never uploads them. A future human-managed GitHub Release must use tag `v<informational-version>` and mark beta versions as prereleases. Stable and `-beta` / `-beta.N` numeric versions are supported. Keep signing and upload authorization separate from this script.

The UTF8 manifest has no BOM or final newline, and is exact canonical JSON with this field order: `app`, `repository`, `version`, `channel`, `filename`, `size`, `sha256`. The detached signature is raw RSA PKCS#1 SHA256 bytes over those exact manifest bytes. The verifier rejects alternate key orders, duplicates, extra fields, unknown keys, malformed values, and mismatched identity. Filenames are fixed. The app hashes the downloaded executable, the staged payload, and the final local swap file immediately before `File.Replace`.

Automatic checks default on, automatic installation off, and beta inclusion off. Checks happen at startup and every six hours, with a separately persisted attempt time and manual ten-second debounce. Automatic installation opts into downloading verified updates and applying them at the next normal launch; it never forces a running widget restart. Manual Download and Restart now remain available when automatic checking is off. Preferences are drafts until Save changes. Turning automatic checks or installation off, or changing channel, cancels current work and disarms scheduled automatic application. Release notes are bounded plain text, never HTML or commands.

Staging lives under `%LOCALAPPDATA%\ProgressPeek\updates`; pending metadata is separate from settings and the check ledger. The helper is a copy of the currently installed trusted executable. It verifies originating PID, process start time, executable path, original/helper hashes, signed manifest, channel, payload size and hash. A readiness handshake keeps the parent alive through origin validation. It waits at most 60 seconds for normal exit and never kills any process. Installation acquires the widget mutex, confines staging to its fixed per-user directory, checks ancestor reparse points, copies the candidate beside the target, then performs an atomic replacement. Non-writable, linked, network, or unexpected locations fail with manual-download guidance and no elevation.

The prior executable remains next to the installation as `ProgressPeek.exe.previous`. If launching the replacement throws, it restores the previous executable and retains the failed candidate as `ProgressPeek.exe.failed`. A successful process start is not proof of long-term application health: there is no boot health watchdog, and crashes after launch require manual recovery. Close the widget and copy the retained previous executable back if needed. Settings, check counts, and user data are not replaced by the installer.

Security scope: this protects against unsigned or modified remote releases and routine filesystem errors. It is not a sandbox or a defense against an attacker already running as the same Windows user, who can modify staging/installed files, replace directories between checks, interfere with named synchronization objects, or race Windows replacement operations. Windows `File.Replace` requires the final hash stream to be closed before replacement, leaving a same-user filesystem race. Administrator/system compromise is likewise outside this boundary. HTTPS requests are unauthenticated, bounded by finite time/byte limits, and limited to fixed GitHub API/release URLs and known release asset redirect hosts. No stored GitHub credentials or model calls are used.

Development verification uses ephemeral RSA test keys and temporary fixture executables only. Never include test keys, personal settings, ledgers, logs, or staging directories in the source archive.
